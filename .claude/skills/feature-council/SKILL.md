# Feature Council — маршрутизация и вердикт

## Purpose / Scope

Определить уровень риска входящего изменения, подключить только нужные линзы и вынести
вердикт до кода. Scope: маршрутизация + продуктово-доменный вердикт. НЕ занимается
реализацией (principal-eng) и выкатом (ship).

## Маршрутизация по уровню риска (первый шаг любой задачи)

| Уровень | Что это | Что подключать |
|---|---|---|
| **L0** | текст, стили, порядок блоков, локальный UI без данных и формул | линзы не нужны → сразу реализация + `ship` |
| **L1** | обычная продуктовая фича (новый UI-блок на существующих данных) | сжатые линзы PM+UX (ниже) → реализация → `ship` |
| **L2** | меняются данные/пайплайн/контракт JSON | + `quant-honesty` обязателен, вердикт письменно |
| **L3** | финансовая модель: portfolio/risk/valuation/backtest/новая метрика | полный совет: все 4 линзы, вердикт письменно ДО кода |
| **L4** | архитектура, CI/CD, security, схема данных | `principal-eng` ведёт + PM-линза «надо ли», ship с расширенной проверкой |

Сомнение между уровнями → берётся высший. Багфикс = уровень того, что чинит
(правка формулы = L3, опечатка = L0).

## When to invoke / When not

- Invoke: каждый новый запрос изменения — минимум для классификации L0–L4 (это 10 секунд).
- Not: продолжение уже одобренной работы; вопросы без изменений кода.

## Сжатые линзы (для L1–L3; полные файлы ролей читать только при реализации)

**PM** (полная: pm-gate): причина вернуться завтра или снятие барьера входа? Не в
СТОП-листе? Оценка: ценность/удержание/сложность/ежедневность. Статика или «ждёт P6»?
**Quant** (полная: quant-honesty): из каких реальных данных; есть ли source+as_of+status;
нет look-ahead; запрещённая лексика; нет полей → честное «н/д», не оценка.
**UX** (полная: ux-terminal): Level 1/2/3; заголовок-вопрос; не плодит плоский список
и дубль-дисклеймер.
**Eng** (полная: principal-eng): что расширяем (grep дублей обязателен); какие гочи
затронуты; миграция схемы нужна?

## Output contract (для L2+; для L1 — 2 строки PM/UX)

```
Уровень: L?
Вердикт: BUILD / BUILD-позже (после X) / SIMPLIFY (объединить с Y) / REJECT (почему)
PM:    ценность · удержание · сложность · ежедневность; статика/P6
Quant: данные = …; классы = actual/derived/…; честно НЕ считаем = …
UX:    место = раздел/уровень; заголовок = «…»
Eng:   расширяем = …; риски = …; миграция = да/нет
```

## Blocking conditions

- L3 без Quant-линзы — запрещено.
- REJECT/SIMPLIFY → сообщить с альтернативой и ждать подтверждения владельца.

## Non-blocking warnings

- Несогласие PM при явном «просто сделай» владельца → исполнять, зафиксировав позицию
  одной строкой. Больше одного раза не спорить.

## Anti-patterns

- Полный совет для L0 (паралич анализа). · Пропуск Quant на L3 «потому что мелочь». ·
  Чтение всех 4 файлов ролей на этапе вердикта (дорого — сжатых линз достаточно).

## Definition of Done

Уровень назван; нужные линзы применены; вердикт в формате выше; при BUILD — передача
в реализацию (principal-eng правила) и выкат (ship).

## Interaction

council → (роли по уровню) → реализация → ship. Ship council не вызывает (нет циклов).

## Пример

«Добавь дневной VaR» → L3 → полный совет → Quant: дневных рядов нет, честное «н/д»
уже реализовано → Вердикт: REJECT (нет данных), альтернатива: месячный VaR уже есть;
дневные ряды = отдельное решение о источнике данных (L2 пайплайн).

*Анти-гниение: код и прод — источник истины; при расхождении со skill — поправь skill.*
