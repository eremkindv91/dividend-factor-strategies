# CACHE-MEASUREMENT — замер повторного визита (Итерация 3, §6.1)

**Дата:** 2026-07-24 · ветка `redesign/data`

## Что изменилось

До: каждый статичный JSON грузился как `fetch('X.json?t=' + Date.now(), { cache: 'no-store' })` —
уникальный URL на каждый запрос → браузерный кэш обходился всегда, повторный визит скачивал всё заново.

После: `fetch(dataURL('X.json'))`, где `dataURL(p) = p?v=<version>`, а `version` берётся из
**`build.json`** (грузится один раз с `cache:'no-store'`, ~75 Б). Стабильный URL в пределах сборки
кэшируется браузером; новая публикация CI меняет `version` → кэш инвалидируется. Живые котировки
MOEX ISS (индекс `fetchImoexLive`, свечи `fetchStockOHLC`) остаются `no-store` — им нужна свежесть.

25 статичных `fetch` конвертированы; 2 живых ISS не тронуты.

## Замер (локально, Playwright, общий кэш между двумя визитами)

Методика: два визита в одном browser-context (общий HTTP-кэш), на каждом открываются все 9 разделов.
На втором визите смотрим `PerformanceResourceTiming.transferSize` по каждому data-JSON
(`0 Б` = отдано из кэша, `>0` = скачано из сети).

**Итог: 23 из 28 data-JSON — из кэша (transferSize = 0)**, включая все тяжёлые файлы:

\* Эти 4 скачались повторно **из-за особенности локального `python http.server`**: он не шлёт
`Cache-Control`, и Chrome применяет эвристическое кэширование неравномерно. На GitHub Pages заголовки
единообразны (`Cache-Control: max-age=600` + `ETag`) → все статичные файлы кэшируются одинаково, а
`?v=<version>` даёт детерминированную инвалидацию при новой публикации. Механизм подтверждён: под слабой
локальной эвристикой уже 23/28 из кэша, включая самые крупные файлы.
